## Naming: passthrough first

Prop names and enum values equal the kit's (Chakra UI v1) wherever a prop is plain data — `fontSize`, `fontWeight`, `textAlign`, `colorScheme`, `variant`, `size`, `spacing`, `direction`, `align`, `justify`, `maxW`, `p`, `bg`, … — so renderers pass them through unchanged. Omitted props take the kit's defaults.

Exceptions, where A2UI needs a different shape:

| Contract prop | Why | Kit |
|---|---|---|
| `text` (Text, Heading), `label` (Button, Tag, inputs) | A2UI reserves `children` for component references | `children` |
| `children` (ChildList), `child`, `trigger`, `content`, `tabs[].child` | component ids or templates, resolved by the renderer | rendered components |
| `value` (Input, Checkbox, Switch, RadioGroup), Modal `open`, Tabs `selectedIndex` | two-way data-model bindings | `value`/`isChecked`, `isOpen`, `index` + change handlers |
| `action`, `checks` | A2UI actions and validation rules | `onClick`, disabled/invalid state and messages |
| `leftIcon`, `rightIcon`, Icon `name` | kit-neutral icon names | icon components |
| Grid `columns` | equal columns instead of raw `templateColumns` | SimpleGrid `columns` |
| List `variant`, Table `columns`/`rows`, RadioGroup `options` | structured data rendered as kit parts | list, table and radio components |


## Styling policy

Components accept token values only. There is no `sx`, `__css`, raw CSS string or responsive object/array syntax in v1:

- **Validation**: every styling value is an enum in the catalog, so the agent's output is checked before it renders.
- **Brand safety**: agents can only pick from the kit's palette, spacing and type scale; a fork changes the values in one file (`src/tokens.ts`).
- **Security**: no arbitrary CSS means no fixed full-screen overlays, `url()` fetches or content injection through styles.

## Catalog rules

Shipped in the catalog document (`instructions`), so every system prompt carries them. Generated from the prop kinds, component roles and function uses (`src/rules/`); only name-free base rules are hand-written (`src/rules/handwritten.ts`):

```text
ui-kit-one rules:
- Use only the components, props and token values of this catalog. No free-form styling: no sx, CSS, pixel values or responsive objects.
- Plan before writing: choose every component id first, emit the root first and each parent before its children, define every id you reference and reuse the exact id string (no renamed or missing ids).
- Keep varying data (lists, table rows, form values, amounts, statuses) in the data model: one updateDataModel message with the whole data object under its value key; bind content to it with {"path": "/..."}.
- A function call has exactly two keys, call and args: omit returnType.
- Never compute styling from data: no conditions, comparisons or ternaries anywhere; every value is a literal, a binding or a function call.
- Never ask the user questions and never wait for an answer: make reasonable assumptions about anything missing or unclear and always reply with the complete UI.
- Surfaces stay on the page for the whole chat (SV-C26): when the user refines a shown surface or acts on it, update that surface (same surfaceId, no new createSurface); create a new surface with a new surfaceId only for a new topic.
- Style props take exactly one literal token from their list, never a {"path"} binding and never a function call: p, px, py, m, mx, my, gap, bg, color, borderRadius, borderWidth, borderColor, shadow, w, maxW, minH, textAlign, minChildWidth, size, fontSize, fontWeight, variant, colorScheme, spacing, boxSize.
- Setting props are literal values too, never bound: centerContent, direction, align, justify, wrap, columns, as, noOfLines, leftIcon, rightIcon, isFullWidth, type, isRequired, options, currency, locale, closeOnAction, Icon.name.
- Data bindings and function calls are for content props only: text, label, isDisabled, isLoading, placeholder, helperText, rows, caption, title, Avatar.name, src.
- State colours: for a few fixed rows write each row explicitly with literal tokens (e.g. Tag colorScheme green / orange / red). In a ChildList template every item gets the same props: give the Tag one fixed colorScheme (or none) and bind only its label.
- Margin, padding, gap, width and height props exist only here: p, px, py, m, mx, my, gap, w, maxW, minH (Box, Center, Container, Flex, Grid); minChildWidth (Grid); spacing (List); boxSize (Icon).
- Heading, Text, Button, Input, Checkbox, RadioGroup, Switch, Table, Tag, Modal, Tabs, Avatar have no margin, padding, gap, width or height props: wrap them in Box, Center, Flex, Grid for spacing.
- The root (id "root") is usually Container, the centred page column; centre a page with it, never with auto margins.
- Id props: children (Box, Center, Container, Flex, Grid, List); trigger, content (Modal); tabs (Tabs). Every id they name must be a component of the same updateComponents message.
- children (Box, Center, Container, Flex, Grid, List) take an array of ids or ONE template object {"componentId": "<id>", "path": "/<array>"} (an object, never an array of templates); inside the template, paths are relative to the item.
- Validate with checks on Button, Input, Checkbox, RadioGroup: each rule is {"condition": <boolean call: required, regex, length, numeric, email, and, or, not>, "message": "..."}; give the submit Button the same checks so it stays disabled until the form is valid.
- Use formatCurrency for money amounts (never write a formatted amount by hand).
- Use formatDate for dates, with the pattern "dd.MM.yyyy" (the renderer locale is ru-RU; month names are not declined).
- Use formatNumber for plain numbers with digit grouping.
- Use formatString for text that mixes literals and data: only ${/path} placeholders, no expressions, operators or ternaries.
- Use pluralize for words that agree with a count.

Interactions:
- Two-way props (Input.value, Checkbox.value, RadioGroup.value, Switch.value, Modal.open, Tabs.selectedIndex): the renderer writes the user's change to the bound path locally, without an agent turn. Always bind them to their own data-model path, never a literal.
- Triggers (Modal.trigger) open their Modal locally; the trigger's own event action is not sent to the agent.
- Checks (Button, Input, Checkbox, RadioGroup) are evaluated locally whenever the data changes.
- Button.action with {"event": {"name": "...", "context": {...}}} is sent to the agent with its resolved context, plus the whole data model when createSurface has sendDataModel: true. Set it whenever the surface has two-way props (Input, Checkbox, RadioGroup, Switch, Modal, Tabs). Answer an event with updateDataModel for changed data (keep it small) or updateComponents for a new layout.
- Button.action with {"functionCall": {"call": "...", "args": {...}}} runs locally, without an agent turn (e.g. openUrl).
- Button.action is required, also on a trigger: give it an event such as {"event": {"name": "modal.open"}}.
```

## How to add or change a component

A component is described once; everything else is generated (catalog.json, system-prompt.md, catalog rules, Interactions, CONTRACTS.md, MAPPING.md). `pnpm check` fails when a generated file is stale (`check:generated`).

| Step | File | What |
|---|---|---|
| 1. Schema | `packages/ui-kit-one-catalog/src/components/<name>.ts` (new) | Zod schema; wrap every prop in its kind: `prop.style(group, tokens, text)`, `prop.option`, `prop.content`, `prop.twoWay`, `prop.child`, `prop.trigger`, `prop.action`, `checksProp` (`src/prop-kinds.ts`); `.describe()` the component, every prop and every item field. |
| 2. Register | `packages/ui-kit-one-catalog/src/components/index.ts` | import and named export, the API in `COMPONENT_APIS` and its role in `COMPONENT_ROLES`. |
| 2b. Public API | `packages/ui-kit-one-catalog/src/index.ts` + `tests/public-api.test.ts` | `<Name>Api` in the explicit export list and in `BEFORE_ENTRY` (DEC-050: every public name is listed). |
| 3. Mapper | `packages/ui-kit-one-react/src/passthrough-components.ts` | pure kit data: one `PASSTHROUGH` line. Needs translation instead: `src/components/<name>.tsx` (new) + one `CUSTOM` line in `src/registry.ts`. The registry is the only renderer list (DEC-007); implementations and MAPPING.md derive from it. |
| 3b. Kit facade | `packages/ui-kit-one-react/src/kit/<name>.ts` + its export in `src/kit/index.ts` and `BEFORE_KIT` in `tests/public-api.test.ts` | only when the kit component is not wrapped yet (the only place that imports the kit; DEC-050). |
| 4. Example | `packages/ui-kit-one-catalog/examples/components/<Name>.json` (new) | one valid snippet (required by the tests). |
| 5. Regenerate | `pnpm build` | catalog.json, prompt, rules, Interactions, CONTRACTS.md, MAPPING.md, server data, validator cases, hand-over bundle; stage them, then `pnpm check`. |

Measured: 9 hand-written files for a pure-data component with a new kit facade (steps 1–4), 6 when the kit component already has a facade, 10 for a custom renderer (its file and a `CUSTOM` line in `src/registry.ts` instead of the `PASSTHROUGH` line); a new two-way, action or trigger prop also needs a gesture in `packages/ui-kit-one-react/tests/behaviour.test.tsx`. The exact list is REMAP.md recipe 7, pinned by `scripts/component-files.test.mjs`. Missing pieces fail fast: no kind or description → the contract module throws (`src/contract-checks.ts`), no role → `createContract` throws, no renderer entry → `src/registry.ts` throws, no example → tests fail.

## How to expose part of a kit prop (no wrapper)

Three cases need no custom component (DEC-046); each is checked against the kit facade's prop types at compile time and follows into catalog.json, the prompt and MAPPING.md on regenerate.

| Case | Files | How |
|---|---|---|
| Value subset (e.g. only `sm`, `md`, `lg`) | 1: `packages/ui-kit-one-catalog/src/components/<name>.ts` | `prop.style(group, pickTokens(sourceTokens, ["sm", "md", "lg"]), text)` (`pickTokens` from `src/tokens/names.ts`; `z.enum(pickTokens(…))` for an option prop). A picked value outside the source list does not compile; the `PASSTHROUGH` line stays unchanged and passes the value through. |
| Renamed or merged values | 2: the schema file (the contract's own values) + its line in `packages/ui-kit-one-react/src/passthrough-components.ts` | `passthrough(Api, Kit, "Kit", { values: { prop: { contractValue: "kitValue" } } })`: applied when rendering and listed in MAPPING.md; every target must be a kit value, every source a contract value, unlisted values must be kit values. |
| Fixed hidden kit prop (e.g. always `size="md"`) | 1: its line in `packages/ui-kit-one-react/src/passthrough-components.ts` | `passthrough(Api, Kit, "Kit", { fixed: { size: "md" } })`: the prop is not in the contract, always rendered with that value, and listed in MAPPING.md; the value must be a kit value and the prop must not be a contract prop. |

Then `pnpm build`. Proof: tests/pick-tokens.test.ts (catalog), tests/passthrough-options.test.tsx (renderer).

## How to change tokens

The token files `packages/ui-kit-one-catalog/src/tokens/*.ts` are the hand-edited source of the contract: they expose a subset of the kit theme to the model. Edit a value or add/remove a key there, then `pnpm build`: the enums in catalog.json, the prompt, CONTRACTS.md and the rules follow. The renderer's kit maps the tokens to its own theme; `check:generated` fails while any generated file is stale.

A missing kind or description makes the contract module throw (`src/contract-checks.ts`), so a half-described component cannot be built. Renaming or re-kinding a prop changes the generated rules and Interactions automatically (tests/catalog-rules.test.ts, tests/add-component.test.ts).

| `length` | `value`, `min?`, `max?` | boolean | Checks string length constraints. |
| `numeric` | `value`, `min?`, `max?` | boolean | Checks numeric range constraints. |
| `email` | `value` | boolean | Checks that the value is a valid email address. |
| `formatString` | `value` | string | Performs string interpolation of data model values and other functions in the catalog functions list and returns the resulting string. The value string can contain interpolated expressions in the `${expression}` format. Supported expression types include: JSON Pointer paths to the data model (e.g., `${/absolute/path}` or `${relative/path}`), and client-side function calls (e.g., `${now()}`). Function arguments must be named (e.g., `${formatDate(value:${/currentDate}, format:'MM-dd')}`). To include a literal `${` sequence, escape it as `\${`.
